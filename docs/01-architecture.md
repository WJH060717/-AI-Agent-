# 01｜系统架构与端到端流程

## 1. 运行边界

一个工作区对应一个授权实验室。P0 以离线日志导入和带速率控制的日志回放为输入；“回放”不是实时监测。传感器可在实验阶段产生数据，但不需要随现场应用一起启动。原型只分析与提出建议，不执行攻击或自动处置。

四个部署服务：`web` 提供静态页面并反向代理；`api` 负责认证、参数校验与查询；`worker` 处理导入、检测、图构建和调查；`db` 保存业务数据。`api` 与 `worker` 使用同一个 Python 代码包，不以服务拆分制造重复模型。原始归档位于共享卷：API 仅经授权读取，worker 写入后封存。

## 2. 模块接口与责任

| 模块 | 输入 | 输出 | 禁止承担的职责 |
|---|---|---|---|
| ImportService | 文件、来源、传感器、时间说明 | 批次、归档对象、解析任务 | 直接生成最终结论 |
| ParserAdapter | 原始记录及来源上下文 | NormalizedEvent 或 ParseError | 猜造缺失资产身份 |
| EntityResolver | 事件、资产/IP 有效区间 | 实体引用与解析依据 | 用永久 IP 代替资产 ID |
| RuleEngine | 事件快照、规则版本 | Finding、规则命中证据 | 使用测试标签 |
| IncidentBuilder | findings、共享强实体、时间窗 | Incident、成员事件 | 把同源 IP 所有行为合成一个事件 |
| GraphService | 事件快照、身份映射 | 节点、边、候选路径 | 无界全图遍历 |
| InvestigationRunner | incident、预算、快照版本 | 工具轨迹、调查状态、报告 | 绕过工具直接访问数据库 |
| EvidenceValidator | 报告草稿、允许证据集合 | 通过/降级/拒绝理由 | 接受模型自证 |
| ReportService | 已校验报告 | JSON、HTML 与版本 | 在导出时重新生成未审计结论 |

每个模块对数据库通过 repository 接口访问。规则、图和 Agent 之间传递 ID 和裁剪后的 DTO，避免重复加载全部原始记录。

## 3. 数据处理顺序

1. API 验证角色、文件大小、格式与幂等键；文件名只作显示，不用于服务器路径。
2. API将上传流写到 `staging_store` 随机临时对象并计算 SHA-256，完成后事务写入 batch、staging manifest 和 job。API不能写已封存归档。
3. worker领取任务，重新校验对象哈希并封存到 `raw_store/workspace/object_id`；同文件系统原子移动，不同文件系统复制、fsync、校验后原子重命名。对象sealed后按行流式解析，每500条提交并保存游标。事务失败产生的孤立对象由清理任务24小时后比对清单处理，不能即时猜删。
4. 无法解析的行写入隔离表并保留原始位置；导入完成给出 accepted/duplicate/quarantined 计数，三者之和等于读取记录数。
5. 规范化事件按事件时间重排，解析实体；不确定身份保留未知。
6. 规则运行于固定 `dataset_version + rule_version`，产生命中与证据；重复执行 upsert，不新增重复 finding。
7. IncidentBuilder 按受影响强实体与相邻活动窗口形成事件；用户也可以从 finding 手动创建事件。候选合并需可拆分且保留合并原因。
8. 冻结调查快照：一个dataset内、明确最多30分钟时间窗内、摄取高水位之前且批次完成的全部合格事件ID，以及规则/知识/图算法版本。incident种子只是其中子集，Agent可在快照内发现尚未关联的事件。快照最多10000事件，超过则要求缩小范围，不能静默漏掉证据。后续到达的数据不能偷偷改变历史报告。
9. 计算图、候选入口和最多 3 条路径；Agent 在同一快照内查询、补证、检查替代解释。
10. 报告校验通过后持久化不可变 report version；失败则展示可解释的部分结果或确定性报告。

## 4. 作业队列和恢复

P0 使用 PostgreSQL `jobs` 表，worker 短事务通过 `FOR UPDATE SKIP LOCKED` 领取，写入 `lease_until`、`worker_id`、`attempt` 后立即提交。实际工作在事务外进行，避免长时间锁住队列。

该语法支持跳过已锁行，适用于队列式领取，但不能据此承诺任意查询得到一致全量视图。依据：[PostgreSQL SELECT](https://www.postgresql.org/docs/16/sql-select.html)。

- 初始 1 个 worker，最多同时运行 1 个调查与 1 个导入；实现上用两个受控执行槽，不做无限并发。
- 心跳每 10 秒，租约 60 秒；租约过期可领取，尝试最多 3 次，指数退避 2/4/8 秒并加抖动。
- 导入按对象/行号确定幂等事件 ID；规则结果有唯一键；报告按 run/version 唯一，重复领取不会重复发布。
- 调用模型存在“请求成功但本地未记账”的窗口，不能承诺外部调用 exactly-once。保存 attempt ID；超时计入预算，最多一次不确定重试并记录潜在重复计费。
- 进程重启从检查点恢复；取消先设置 `cancel_requested`，每次工具调用前及节点结束检查，取消后的晚到模型响应不发布。
- 队列状态：`queued → running → succeeded | partial | failed | cancelled`，超时用 `failed` 和 `error_code=TIMEOUT`；调查内部状态另见 Agent 文档。
- 状态更新附 `version` 做乐观锁；过期 worker 不能用旧租约覆盖新 worker 结果。

## 5. 回放与迟到数据

离线批次按 `event_time,event_id` 排序处理；回放器按固定速率投递原始事件，显示原始时间与当前回放进度，不伪造当前发生时间。每次回放创建独立analysis_session，引用原dataset和原event_id，不改写或重复持久化原事件。session_members按速率增加可见事件；规则状态、finding、incident和调查限定workspace+dataset+analysis_session，避免两次回放串联。同session重试按event_id幂等。初次离线分析也有一个默认analysis_session，全部合法事件一次可见。摄取吞吐测试单独使用空dataset原始导入，不将回放已有事件或去重缓存命中计作新增摄取。

若做 P1 流式输入，默认 30 秒迟到容忍；watermark 前后分别处理，迟到事件写入并标记，触发新分析版本而非覆盖报告。时钟不确定度影响关联强度；不存在可靠校时数据时，不自动把时间偏移拟合成“更像攻击链”的结果。

## 6. 存储一致性与快照

数据库是派生状态权威；原始归档是引用内容权威。`raw_objects` 保存 `sealed` 状态，只有已封存对象可进入分析。事件、规则结果、图边、报告不得引用未完成导入的对象。

一次报告包含 `snapshot_id`，查询工具强制约束到该快照允许事件集合；报告打开时默认加载该版本，页面明确显示“新数据可重新调查”。新调查产生新 run 和报告版本。

图与报告都可重建，但重建须保留旧版本及参数，不能更新历史报告的 `created_at` 冒充新结果。证据对象损坏时报告仍可查看，但对应引用标记不可验证，禁止显示绿色验证通过。

## 7. 可观测性

所有服务输出结构化 JSON 日志：`timestamp, level, service, request_id, job_id, run_id, action, duration_ms, status, error_code`。原始日志正文、令牌、完整提示词默认不进入服务日志。

最少指标：导入行数与失败数、队列长度、最老任务等待、规范化吞吐、各规则命中、图节点/边数量、查询延迟、Agent 工具调用数、预算消耗、引用校验失败数、报告降级率、CPU/内存/磁盘。三周可用简单日志聚合和前端状态页，无需额外监控集群。

## 8. 资源与容量推导

按平均规范化事件 2 KB、10 万条估算，事件 JSON 原文约 200 MB；索引与行开销先按 2～3 倍预留，约 0.4～0.6 GB，必须实测。50 EPS × 1800 秒 = 9 万条；与 10 万条验收规模一致。该速率若连续一天会达 432 万条、原文约 8.64 GB，故本方案不支持不受控全天采集。

原始 PCAP 体积单独计费且不默认全部保留；三周原型总数据先限制 10 GB，归档+备份+镜像合计建议预留 40 GB。单文件上传上限 100 MB；较大日志由离线切分工具生成带父 manifest 的分片，不通过 API 上传压缩包。内存过限时减少图规模和并发，不能偷偷丢证据。

## 9. 三周内不引入的复杂度

不做全自动根因定论，不以 LLM 生成查询语言，不做多智能体互相自由对话，不训练大模型，不建实时流计算集群，不混用多个主数据库。架构通过接口保留替换能力，只有实际瓶颈证据才启动 ADR 变更。
