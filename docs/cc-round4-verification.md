# CTU-13 第四轮：抓包补证与混合编码查询（dev24）

日期：2026-11-17。用户授权独立环境补充剩余21条官方恶意连接的证据与检测，不修改8080，不调用付费模型。本轮是已见样本上的开发验证，不是盲测或正式检测成绩。

## 实际结论

加入完整连接上下文后，官方恶意连接的去重候选覆盖由 **5/26 增至6/26**，新增1条、剩余20条。仅输入上轮剩余21条时仍是 **0/21**：新R11要求至少两条独立异常连接，而该子集只有1条满足单连接形态；与原先已覆盖的2条异常连接共同输入后才形成候选。因此不能说该新增连接已经具备孤立检测能力。

新增覆盖的Bro UID是 `CqHf0wiBJbjQOoJNh`。旧Bro记录为S0、2个发送包、零有效载荷；官方感染主机侧PCAP却包含完整GET与404响应。两种观测并存，未回写旧日志、未把差异归咎于某个未核实原因。R11覆盖3条抓包连接，其中另2条此前已被Bro侧R10覆盖；同一官方连接跨探针只计一次。

**候选对应官方恶意标签不等于证实控制成功、命令含义或进程归属。** 3条R11请求均是404，报告保留 `maliciousness=unknown`。

## 原始证据与适配

官方来源：[CTU-Malware-Capture-Botnet-48目录](https://mcfp.felk.cvut.cz/publicDatasets/CTU-Malware-Capture-Botnet-48/)及其中 `botnet-capture-20110816-sogou.pcap`。官方公开完整PCAP来自感染主机接口；整个网络的完整载荷捕获未公开。公开的全网截短捕获不能补足正常HTTP响应内容。

- 新PCAP：18,868,213字节，20,663个物理包，SHA256 `ff5c18adaa6a4681df1db43d0eac10d05e65d51931d5380ca54ceff0d005d2c5`。
- 既有官方标签文件：SHA256 `df0b5338190b967bd340a0d6c1bb3c34d1bbfb4b7ffa764c2dd26f77f1a26680`，仅离线使用。
- 26条选定连接全部适配成功，恢复78次HTTP事务，零拒绝。重传字节去重，未把重复包当重复请求。
- 21条待补证连接：Bro侧72次HTTP，PCAP侧73次HTTP。19条CC108网页外形连接共71次事务，在PCAP中均有200响应；旧Bro其中62次缺状态、9次已知200。响应实体外形为39 GIF、21 JPEG、7 gzip、2 ICO、1 PNG、1 other；只识别格式，不执行或解压内容，也不将其判为正常。
- 另一条 `CWhYaxEr6mIvRe9Ih` 仍为浏览器外形请求、404，现有结构证据不足以区分普通遥测与恶意控制。
- 同五元组跨采集点时间差为4.062560–4.064944秒。保留各自原时间、各自传感器与独立UID，**没有在线拟合校时或跨探针强连**。离线对应依据是所选范围内唯一完整端点元组及原捕获来源，不构成socket或操作者身份事实。

PCAP字节中的3条异常查询为ASCII混合百分号形态，而Bro输出包含非UTF8字节；保留两份原件和各自形态，不把日志表示等同线上的原始字节。新规则只统计合法 `%HH` 片段中的非ASCII字节及非法百分号数，不对非法查询部分解码。HTTP分帧范围参照 [RFC 9112](https://www.rfc-editor.org/rfc/rfc9112.html)，百分号语法参照 [RFC 3986](https://www.rfc-editor.org/rfc/rfc3986.html)。

## 实现与兼容范围

源码版本0.1.0.dev24，迁移仍0006_d9。R01–R10所有已有配置和冻结不改，旧R07–R10的Zeek来源条件不扩展；新增独立 `rules/R11.json` / `rules/cc-encoding-freeze.json`。

- `packages/ingest/pcap.py`：有界classic PCAP/Ethernet/IPv4/TCP适配，SYN与ACK核验、TCP重组/冲突/缺口拒绝、生命周期复用拒绝、FIN尾部完整性检查及请求/响应包序和ACK配对。全流验证后才生成记录；不修改原包。
- `packages/ingest/http_wire.py`：有界HTTP/1分帧，内容长度或chunked，拒绝歧义头部、截断及未支持的分帧；仅保留安全编码计数和响应格式摘要。
- 新导入格式 `pcap` / `pcap_http`，独立pcap传感器族。网页自动识别派生JSONL，新增两个短选项。尚不支持直接上传二进制PCAP。
- HTTP schema1.5增加可选 `query_encoding` / `response_shape`。旧Zeek HTTP仍用原schema1.4/解析语义，旧数据不补写。原始请求/响应base64仅留本地原件，模型、证据投影、报告和导出不带这些内容。
- R11仅针对pcap来源：GET/POST、同采集范围/源/目的IP:port/Host，至少32字节查询，无明文键值分隔符，至少1个非法百分号与至少1个有效非ASCII转义；至少2条独立TCP连接、600秒保守窗口、唯一完整连接关联、已分帧响应。不会凭IP、文件外形或官方标签触发。
- `scripts/pcap_http_sample.py`为可复用本地适配入口；`eval/ctu13_cc_round4*.py`仅用于离线选样/官方标签对照，应用镜像不含eval、原始抓包或官方答案。

证据核验分两层：离线重新适配并核对PCAP哈希、包号/字节区间及派生记录；API `evidence.verified`核对已导入JSONL原始对象。网页没有直接核验外部PCAP文件，不得混称。

## 剩余缺口与未验证项

1. 20条官方恶意连接仍无候选：19条网页资源外形、1条浏览器外形404请求。响应魔数/200不证明正常，官方恶意标签也不能补造命令语义。仍需可验证的响应内容语义、主机进程/socket或同源行为证据；本轮没有执行捕获载荷或主动访问远端。
2. 新增覆盖依赖完整连接上下文；剩余21条独立输入仍未覆盖，未通过放宽最少连接数掩盖该限制。
3. R11真实正常PCAP对照、其他CTU场景、独立盲测、普通旧编码/二进制遥测/代理的普适误报率尚未验证。真实正常Bro的旧R05候选仍是误报风险。
4. 原生二进制网页上传、pcapng、IPv6/VLAN、IP分片、TLS/HTTP2、HEAD/1xx/close-delimited等格式不在支持范围。适配拒绝不能解释成“无恶意”；当前证据只涵盖捕获到的明确事务，不证明整个网络/会话完整。
5. 多文件重叠抓包去重、100000规模新规则性能、其他生产时钟条件未验证。单文件内重传去重不等于跨文件会话去重。
6. 真实控制成功、进程身份、操作者、完整攻击因果及真实LLM效果未验证。确定性报告不能替代真实模型验收。
7. 未部署8080、未测试生产重启切换或存量补写；本轮只交付独立验证候选，保留用户原服务与原数据。
