# D11 实施与证据台账

## 目标与设计

按 PROJECT_SPEC、docs/06 的 D11 行及 docs/07 完成现有 P0 的实测、修复和离线评估入口。保持 D10 原候选不变；继续 Python/FastAPI、现有队列与 React，不添加服务或训练模型。独立数据/标签和真实 LLM 不具备时，记录 blocked，不能从开发夹具推导正式成绩。

方案：直接复用实际 API/worker/检测/图/Agent，离线评估器只在运行结束后接触真值。选择此方案是为了让性能和预测来自真实代码；重写模拟算法不能验证现有系统，扩展在线评估服务不属于 P0。实现细节由助手在现有授权范围内决定，沿用内联实现与最终一次独立审查。

当前发现：检测每批发布时读取会话，超过10000事件会抛RULE_SCOPE_TOO_LARGE并回滚发布；图超过500节点/1000边抛异常；空态需核查实际组件。先用反例固定行为，再做有界且明确提示覆盖限制的最小修复。检测阈值、身份规则、旧快照/报告和数据库冻结基线不变。

## 全局约束

- 只用授权本地合成输入及隔离临时库；不扫描、不攻击、不上传日志；不改用户数据库、密钥或旧候选。
- schema_v1–v6冻结；必要改表必须新迁移。当前计划不改表。
- 原始数据、报告、快照不可变；Queue.guard、lease/version、调用前预算与不退款保持。
- API/Agent不导入eval或真值；formal与engineering、live/stub/fallback/cached显式区分。
- 性能协议在运行前固定：500条/10秒/1800秒，90000条新数据；100000事件后100次串行查询。任何缩短运行只能称smoke，不改目标抹掉失败。
- 保留每次预测、失败、计数和耗时；零分母记null/N/A；不以单次本机结果证明生产容量。

## 审查重点

1. 规模上限不能造成已接收原始数据静默丢失，也不能把未检测部分称为检测完成。
2. 图裁剪前校验全部输入范围；不得悬空边或用后续越界事件补关系。
3. 指标匹配不得贪心少配、重复抬召回、将未知当负例或将零样本算100%。
4. 真值路径/内容不能进入运行组件；版本漂移、缺组别、失败或不完整输入不能算正式评估完成。
5. 基准必须走真实新摄取，保留失败/排队/资源记录；重启不能重置预算和before或重复发布。
